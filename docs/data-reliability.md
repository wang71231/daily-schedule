# 课时数据可靠性排查（2026-11-10）

用户反馈：原 GitHub Pages 页面有时丢课时。没有取得发生问题时的手机存储快照，因此不能断言每一次历史丢失都由同一原因导致，也不能声称已经找回缺失记录。

## 可复现的问题

1. 旧 `localStorage` 采用“读全部 → 修改 → 写全部”。两个标签页读到同一旧值后交错写入，后一个会覆盖前一个新增。
2. `trainingLogsLastGood` 只有一份。删除一条后再改另一条，恢复副本也不再含被删记录。
3. 清空/删除/导入涉及多次独立保存，存在保存失败后界面先改变、只保存一部分的风险。
4. 小时输入仅在 `change` 时保存，尚未离开输入框就刷新，修改可能尚未保存。
5. 旧导入只检查外层容器，错误记录可能写入后在渲染阶段出错。
6. 原服务器同步脚本在发送期间发生新编辑时引用作用域外变量，误报网络错误；整份覆盖与旧版本选择也缺少可靠的共同基准。

`tests/reproduce-old-storage.cjs` 可对保存的旧页面复现前两项，输出两个 false。

## 已实施的修复

- IndexedDB 在同一事务中读取最新数据、修改、验证、保存当前版本和历史。失败全部回滚。
- 旧键保留，首次迁移后不删除；旧页再写入时有合并入口及旧数据快照。
- 最近 100 次本机历史可下载和恢复。恢复会先保存当前状态。
- 输入有效数值即保存；保存失败有明确提示。导入先全量验证，合并操作原子提交。
- 同步以共同基准做三方比较：保留上传期间新修改，独立更改合并，重复编辑冲突暂停；明确处理删除，不用简单对象展开复活被删除记录。
- 云端来源标识和版本检查防止换库/回退静默覆盖。D1 将旧版本存档和更新放在一个事务中。
- 登录限速、CSRF、同源检查、带 Secure/HttpOnly 的会话和改密失效逻辑保留。

## 验证

- 真实 Chromium 隔离上下文：旧数据升级、多个标签页并发、删除后再保存的恢复、事务异常、配额失败、错误导入、分钟换算、输入未失焦即刷新、上传中继续编辑、多设备独立更改及冲突、旧页继续写入、断网刷新。
- SQLite 执行真实 SQL：版本历史、旧版本拒绝、错误数据库标识拒绝、数据校验、事务失败回滚、认证、限速、改密与会话失效、三方合并的删除冲突。
- 本地 workerd + D1 完整联调：登录、资源路由、实际保存和刷新、另一个浏览器上下文读取、云端历史、改密码、工资规则与手机宽度。

测试使用独立的合成记录，不读取用户浏览器配置、不修改线上课时。

## 仍然存在的边界

本机数据库和本机快照都可能随浏览器网站数据一起清除。无痕模式、不同网址、不同浏览器、系统清理或换设备不保证保留数据；事务机制不能替代异地备份。

在 Cloudflare 完成真实部署及手机数据导入之前，原 Pages 的记录仍只有本机副本。上线后也应定期导出 JSON，并使用 D1 导出/平台恢复能力保留异地备份。Git 仓库不存真实课时数据。
